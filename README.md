# Soda — умный подбор подрядчиков

Проект команды Soda для HackAlem AI по кейсу Firebird «Умный подбор подрядчиков» (#79-lite).

## Текущий статус

Согласована концепция и основной пользовательский сценарий. Приложение пока не реализовано: в репозитории нет исполняемого кода, датасета или настроенных внешних сервисов. Стек и AI-модели окончательно не выбраны.

Ниже описан планируемый результат, а не готовые возможности.

## Для кого и зачем

Заказчик уже получил каталог event-подрядчиков своего города. Сервис поможет выбрать из него до трёх подходящих вариантов и объяснит выбор каждого конкретными фактами из каталога.

## Пользовательский сценарий

1. Пользователь описывает мероприятие своими словами.
2. AI извлекает параметры и пожелания, например «камерная атмосфера» или «репортажная фотография».
3. Открывается окно подтверждения с редактируемыми полями. Недостающие обязательные сведения нужно дополнить.
4. После нажатия «Подобрать подрядчиков» сервис проверяет ограничения и сравнивает подходящих кандидатов по пожеланиям.
5. Пользователь получает до трёх карточек и может вернуться к изменению параметров.

Обязательные поля: город, дата, формат мероприятия, категория подрядчика, бюджет в тенге. Дополнительные: язык и длительность. Пожелания отображаются отдельно от строгих ограничений.

## Правила подбора

- Код проверяет город, категорию, дату, начальную цену, формат и указанные дополнительные ограничения. Занятые на выбранную дату подрядчики исключаются, включая площадки.
- AI участвует в понимании запроса и смысловом подборе среди прошедших проверку профилей. Смысловая близость не доказывает выполнение строгого требования.
- В карточке — имя, категория, город, цена «от» и 1–2 предложения с конкретными отличительными фактами. Не допускаются выдуманные услуги, опыт, отзывы или гарантии.
- Если подходит меньше трёх, показывается фактическое число и причина. Отдельно различаются отсутствие категории в городе и отсутствие кандидатов, проходящих условия.
- Одинаковый запрос при неизменных данных должен давать одинаковый порядок карточек. Ориентир времени ответа — до 10 секунд.
- Условия не ослабляются без согласия пользователя. При сбое AI нужен понятный запасной сценарий без имитации смыслового подбора.

## Предварительная архитектура

Рассматриваем Go для серверной части и React + TypeScript + Vite для интерфейса. Для 66 профилей планируем загрузку JSONL в память без отдельной базы данных.

LLM — языковая модель — будет разбирать запрос и помогать выбирать факты для объяснений. Для сравнения пожеланий с описаниями рассматриваем эмбеддинги: числовые представления смысла текста. Окончательный выбор моделей и сервисов ещё впереди; доступ к API Firebird не подтверждён.

Для повторяемого порядка потребуется зафиксировать модель, версию данных, представления текстов и правила сортировки; при равенстве использовать стабильный `id`. Без пожеланий рассматриваем сортировку по начальной цене, затем по `id`. Одних настроек случайности модели или кеша недостаточно для гарантии повторяемости.

## Данные и ограничения

По документу кейса организаторы предоставляют `hackathon-dataset-anonymized.jsonl` на 66 профилей, а также CSV и HTML-превью. Сам датасет ещё не добавлен в репозиторий и не изучен.

- `price_from_kzt` — начальная цена за мероприятие, а не гарантированная итоговая стоимость и не почасовая ставка.
- Календарь покрывает 23.09.2026–31.12.2026. За его пределами отсутствие даты в `busy_dates` не подтверждает доступность; поведение интерфейса для таких дат предстоит определить.
- `max_hours: null` означает, что услуга не привязана к присутствию на площадке, и само по себе не исключает профиль.
- Нужно сохранять флаги `synthetic`, `city_imputed`, `price_imputed`. Если команда добавит свои синтетические профили, их нужно отличать от исходного каталога, в котором уже есть синтетические записи.
- API-ключи должны храниться только на сервере и не попадать в репозиторий.

Бронирование, заявки, оплата, уведомления подрядчикам и дообучение модели не входят в план первой версии.

## Запуск и проверка

Команд запуска и автоматических проверок пока нет. Они будут добавлены вместе с реализацией. Развёрнутой версии пока нет.

План демонстрации после изучения данных:

1. Массовая категория на осеннюю дату с несколькими кандидатами и различимыми объяснениями.
2. Редкая категория с честным объяснением числа результатов.
3. Запрос без результата с понятной причиной.
4. Повтор запроса с тем же порядком карточек.
5. Изменение даты, которое меняет выдачу из-за занятости, с пояснением причины.

Перед сдачей необходимо обновить README по фактической реализации, добавить воспроизводимый пример проверки, отправить итоговый код в командный GitHub-репозиторий и сдать решение через платформу хакатона.
